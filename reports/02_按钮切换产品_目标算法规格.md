# 按键切换人声：目标算法规格（定稿 v2）

> ⚠️ **本文是立项期的规格草案，其中"尚未训练""0.584M / 2.217 GMAC·s⁻¹""低频保护 <120Hz"
> 等条目已被实测取代。当前状态与出货配置见 `reports/08_v4训练与瓶颈诊断.md`：**
> 真实规格 **0.5297M 参数 / 517KB INT8 / 1.226 GMAC·音频秒⁻¹**；权重已训练到可用；
> 出货配置 = **`results/k3s_model.pt`（每首 3 个片段、900 s）+ 推理期 `<250Hz` 掩码置 0**；
> 量化 **INT8 权重(per-channel) × INT12 激活 × uint8 掩码 / INT32 累加**（deploy12 ≈ 29 dB，不可闻）。
> 本文其余部分保留为设计依据。

> 产品定义：板上一个按键，按下人声消失、器乐继续播放；再按一次人声恢复。
> 平台：Xilinx Zynq-7020（XC7Z020-1），PL 侧 NPU 加速
> 评测素材：`Le Youth - Chills`（44.1kHz 立体声 / 320kbps），60–100s 片段

---

## 0. 结论速览

| 项目 | 结论 |
|---|---|
| 是否要 NPU | **必须要**。免费的反相消声会连整首歌一起删掉（见 §2） |
| 目标算法族 | **因果频域 U-Net，128 频带，2-stem**（预测人声掩码，伴奏 = 混音 − 人声） |
| 规模 | 0.584M 参数 / 571KB INT8 权重 / 2.217 GMAC·s⁻¹ |
| 通路延迟 | **110 ms**（恒定偏移，纯播放无感，见 §3.1） |
| 按键响应 | **≈30 ms**（模型常开，按键只是切乘数，见 §3.1 / §4） |
| 按键开销 | **零额外算力** —— 按键只是一次乘法（见 §4） |
| 是否已验证 | **架构已实例化并验证通过**（因果性、算力、管线无损），但**尚未训练** —— 没有权重，因此没有任何"它自己分离出来的"音频（见 §9.1） |
| 相比上一版的变化 | **模型本身不变**，变的是分块大小与 DDR 带宽预算 |

**核心判断：按键这个需求不会让你换模型，只会让你把省下来的延迟换成更宽松的 DDR 带宽。**

---

## 1. 产品形态带来的两个推论

### 1.1 延迟约束被放宽（有利）
上一版按 `<100ms` 硬约束设计。但按键产品的音频是**录播回放**，不是实时返听：
- 没有"自己唱给自己听"的监测需求，所以不存在监听延迟问题；
- 按键到听感变化的延迟在 **200–300ms 以内**，用户基本无感。

因此延迟不再是紧约束，可以把预算花在别处。

### 1.2 但引入了三个新的硬要求（不利，见 §5）
按键不是"多一个开关"这么简单，它把评测口径整个改了：
- 离线评测看 40 秒片段，用户实际是**连续听 4 分钟**；
- 任何帧间抖动、爆音、卡顿都会被放大成"产品坏了"。

## 2. 先排除免费方案：反相消声（center cancellation）

写 `L = M + S`、`R = M − S`，卡拉OK输出取侧信号 `S = (L−R)/2`，丢弃中置 `M = (L+R)/2`。

实测（`results/button_baseline.json`）：

| 指标 | 反相消声 | HTDemucs | 判定 |
|---|---|---|---|
| 人声残余（越低越好） | **−52.7 dB** | −13.9 dB | 看起来碾压 |
| 整体电平损失 | **−12.3 dB** | −0.2 dB | 只剩 **5.8%** 能量 |
| 与真实伴奏相关度 | **−0.008** | — | 基本为零 |
| 30–120Hz（底鼓/贝斯）损伤 | **−20.7 dB** | −0.0 dB | 律动彻底消失 |

**这首歌 94% 的能量在中置声道**（含贝斯、底鼓、pad），左侧整体 L/R 相关度高达 0.883。

结论：
1. 反相消声不可用 —— `−52.7 dB` 是"交白卷"式的好看数字，因为连音乐一起删了。
2. 更重要的推论：**这首歌的空间线索不足以分离声源**。模型必须**按音色内容**判断，不能依赖"居中的就是人声"。这是神经网络擅长、传统 DSP 做不到的事，也正是 NPU 的价值所在。

对照组：Demucs 家族对每个频段的改动都在 **1 dB 以内**，即"它听上去还是那首歌"。

## 3. 延迟预算重新分配

延迟公式（`scripts/06_fpga_budget.py`）：

```
latency = STFT窗(n_fft/sr) + (3 + chunk_frames) × hop/sr
```

以 128 频带、`enc=(32,64,96,128)` 为例，扫描分块大小：

| chunk 帧数 | 延迟 | 算力 | RTF | 片上激活 | DDR 带宽需求 | 门限 |
|---|---|---|---|---|---|---|
| 4 | 64 ms | 2.217 | 0.101 | 276 KB | 25.2 MB/s | GO |
| 8 | 87 ms | 2.217 | 0.101 | 364 KB | 12.6 MB/s | GO |
| **12** | **110 ms** | 2.217 | 0.101 | **452 KB** | **8.4 MB/s** | **GO ← 推荐** |
| 16 | 134 ms | 2.217 | 0.101 | 540 KB | 6.3 MB/s | 激活超限 |
| 24 | 180 ms | 2.217 | 0.101 | 716 KB | 4.2 MB/s | 激活超限 |

关键洞察（反直觉）：
- **加大分块能大幅降低 DDR 带宽需求**（权重加载次数变少）：25.2 → 8.4 MB/s，3 倍余量。
- **但会线性增加片上激活**（跳连需要保留整个分块），而 BRAM 只有 630 KB。
- 所以存在最优点：**chunk = 12 帧**，延迟 110ms，激活 452KB，带宽 8.4MB/s。

这正是按键产品买到的东西：**用 46ms 额外延迟换 3 倍的 DDR 带宽余量**。对连续播放的产品，带宽余量直接等于"不卡顿"。

### 3.1 澄清："110 ms"指的不是按键反应时间

这是最容易误读的一处。**110 ms 是音频通路延迟，不是"按下按键后要等 110 ms 人声才消失"。** 三个时间必须分开看：

| 名称 | 定义 | 数值 | 用户感知 |
|---|---|---|---|
| **通路延迟**（本文所有"延迟"默认指这个） | 此刻耳机里放出的声音，是多久之前采集的 | **110 ms** | 无感。它是**恒定偏移**，不随时间累加，纯音频播放听不出来 |
| **按键响应** | 按下按键 → 听感上人声消失 | **≈30 ms**（`g` 斜坡）+ 输出缓冲数 ms | 这才是用户按下去时实际感受到的那个延迟 |
| **冷启动预热** | 开机 / 起播 → 第一次输出分离结果 | **≈110 ms** | 只在开机时出现一次 |

**为什么按键能比通路延迟更快？** 因为模型是**持续运行**的：它一直在吃音频、一直在算人声估计。按键只是把输出级的乘数 `g` 从 0 改到 1（见 §4），是**在通路末端**生效的，不需要等通路里的任何东西排完队。

**这带来一条硬性设计要求：`g` 必须作用在输出级（`out = mix_delayed − g · vocal_est`），不能作用在输入级。** 如果改成"按键才启动模型"（例如为省电），按键延迟就会真的变成 110 ms，而且会听到一段断音——**必须保证模型常开，或至少预先填满输入缓冲**。

**一个与 DJ 用途相关的提醒**：110 ms 的恒定偏移对"整条链路都走这个盒子"的播放完全无害。但若把它与**另一条未经处理的通路**（如另一台唱机、直通监听）同时送到同一只耳朵或同一个调音台，两者之间会出现 110 ms 的固定错位，节拍会对不齐。这类场景需要让两条通路等长延迟。

### 放宽延迟后能加大模型吗？
不能。实测：

| 频带数 | 通道 | 参数 | RTF | 激活 | 判定 |
|---|---|---|---|---|---|
| 128 | (32,64,96,128) | 0.584M | 0.101 | 452 KB | GO |
| 128 | (48,96,128,192) | 1.190M | 0.211 | 1042 KB | 激活超限 |
| 256 | (32,64,96,128) | 0.584M | 0.202 | 1080 KB | 激活超限 |
| 256 | (64,128,160,224) | 1.820M | 0.702 | 1688 KB | 全项超限 |

**瓶颈依然是 BRAM 而非算力**（RTF 0.101 时算力只用了 10%）。所以目标规格维持 128 频带。

## 4. 按键的实现：零额外算力

```
out = mix_delayed − g · vocal_estimated
```

- `g = 0` → 原混音（有人声）
- `g = 1` → 混音 − 人声（纯伴奏）

按键只切换 `g`。**模型始终在跑，不需要重算，按键零开销。**

唯一要求：`g` 必须**渐变（约 30ms）**，不能硬切。硬切会在波形上产生阶跃，听感是明显的"啪"声。

## 5. 按键产品引入的新工程要求

### 5.1 防爆音（click-free）
`g` 的斜坡时间 20–50ms。这是硬件/驱动层面必须做的，不能省。

### 5.2 防音乐噪声（musical noise）—— 这是第一号杀手
因果/流式模型逐帧估计掩码会有帧间抖动，输出会带"咕噜咕噜"的水声 artifacts。
在离线评测里不明显，**在连续播放时极其刺耳**。

对策：**把省下来的延迟预算花在"掩码时间平滑 / 轻微前视"上，而不是花在加大模型上。**
实测收益：加入 100–200ms 前视 + 掩码时间平滑，比单纯把参数量翻倍对听感的改善更明显。

### 5.3 防卡顿（绝对不能掉帧）
连续播放要求**每一块都按时完成**，不是平均达标。
- RTF 目标 ≤ 0.5（现有预算模型已按此设定）
- 推荐按 chunk=12 的 8.4 MB/s DDR 预算设计，留 3 倍余量
- 必须做双缓冲 / ping-pong，避免 DMA 与计算争抢

### 5.4 评价指标要改（SDR 不是对的指标）
按键产品的听感由两件事决定，权重不同：
- **残余人声（ghost vocal）**：用户按了按键还听到人声 → 明显失败
- **器乐损伤**：镲片被吃掉、pad 变空 → 明显失败

建议训练损失对"器乐保真度"加权，而不是直接优化 SDR。

## 6. 低频保护（低成本高收益）—— 已实测定型

实测发现 30–120Hz 是全场最脆弱的部分（反相消声在这里损失 20.7 dB，律动直接消失）。

**已定规格：把学习到的人声掩码 `< 250 Hz` 强制为 0（该段低频直通）。**
（原估计是 ~120 Hz，2026-09-13 用固定留出集扫描后**上修到 250 Hz**，理由见下。）

- 人声基频主要在 100–350Hz 以上，牺牲极小；
- 保住底鼓与贝斯 = 保住这首歌的律动；
- 计算成本**零**（PL 上只是一个频带索引比较器，0 个 MAC）。

### 为什么这条比预想更重要

`band_edges = geomspace(30, 16000, 129)` 是对数带，而 STFT 频点间距是 43 Hz →
**49 个最低频带整列为 0**（实际只有 79 个有效带）。但**合成矩阵仍然把 <500 Hz 的频点
路由经过这些带**，于是那一段应用的掩码是"网络对常数零输入的响应"，即一个**与歌曲无关的常数**。
实测 **700 Hz 以下人声掩码均值 = 0.2597**：

> 也就是说，按键按下时，**无论歌里在放什么，底鼓和贝斯都会被无条件减掉 26%**。

在固定 24 首留出集（14 首可评分）上扫 cutoff：

| cutoff | 人声（可评分中位） | 伴奏（可评分中位） | 人声变好 | 伴奏变好 |
|---|---|---|---|---|
| 关 | 2.780 | 11.154 | — | — |
| <150 Hz | 3.348 | 11.514 | 13/14 | 10/14 |
| **<250 Hz** | **3.521** | **11.520** | **12/14** | **12/14** |
| <300 Hz | 3.159 | 11.593 | 11/14 | 11/14 |
| ≥350 Hz | 3.52 → **1.69（崩塌）** | — | — | — |

听感证据（`Jerro, Sophia Bel - Demons.mp3`，有真人声）：伴奏 25–120 Hz 变化
从 **−0.37 dB 变成 −0.00 dB**（低音完全不掉），同时人声 +4.99→+5.36、伴奏 +10.00→+10.19。

已实现为 `separate(net, mix, Wa, Gs, device, lf_kill_band=...)` + `lf_kill_band_for(hz)`，
默认 0 以保持旧测量可复现；出厂路径传入 250 Hz 对应的频带号。详见报告 08 §10。

## 7. 训练数据策略：绕开 22.7GB 下载

按钮产品只需要一个**人声掩码**，不需要完整的 4-stem 数据集。可行路径：

1. **合成配对（主力）**：任取伴奏 + 任取清唱，随机增益/EQ/声像/混响后混音。清唱与伴奏素材公开可得，且随机化能显著提升真实歌曲上的鲁棒性。
2. **伪标签蒸馏**：已下载的 HTDemucs（80MB）对无标注音乐打伪标签 —— 本机可用，无需外网。
3. MUSDB18-HQ 只在需要**绝对 SDR 数值**时才有必要（当前受控代理下实测 ≈300KB/s，22.7GB 需 20 小时以上，暂缓）。

**下载受阻不再是阻塞项。**

## 8. 不推荐的结构

| 结构 | 原因 |
|---|---|
| BiLSTM / 双向 RNN | 需看全曲 → 延迟无界；且时序依赖串行，喂不满 220 个 DSP |
| Transformer / 注意力 | HTDemucs 里占 75% 参数、63MB 激活；数据依赖的 gather + softmax 使阵列利用率掉到 15% |
| 非因果大 U-Net（Spleeter 默认） | 延迟与激活双超标 |
| 波形域（Wave-U-Net 类） | 44.1kHz 下波形域算力是频谱域的数十倍 |

**唯一值得花一周验证的替代方案**：Band-split RNN（MDX-Net / Bandit 系）。
它的循环是**按频带独立**的，128 条频带可并行展开，理论上仍能填满阵列；风险是每带内部的串行深度。属于"值得 benchmark、但不要提前承诺"的选项。

## 9. 目标规格（定稿）

| 项 | 值 |
|---|---|
| 任务 | 2-stem（人声 / 伴奏），只输出伴奏 |
| 结构 | 因果频域 U-Net，2D 膨胀卷积，无 RNN / 无注意力 |

| 频带数 | 128 |
| 编码通道 | 32 / 64 / 96 / 128 |
| 参数量 | 0.584 M |
| 权重（INT8） | 571 KB（FP32 为 2.2 MB） |
| 算力 | 2.217 GMAC·s⁻¹ |
| 7020 实际 RTF | 0.101（算力余量 10 倍） |
| 分块 | 12 帧（≈70ms） |
| 通路延迟（端到端） | **110 ms**（恒定偏移，非按键反应时间） |
| 按键响应 | **≈30 ms**（前提：模型常开、`g` 作用在输出级） |
| 片上激活 | 452 KB / 630 KB BRAM |
| DDR 带宽需求 | 8.4 MB/s（余量 ~70 倍） |

| 按键 | `g` 斜坡 30ms，零算力 |

### 9.1 实测修正（见 `03_目标模型验证报告.md`）

本表在 2026-09-12 之后已被**实例化验证**。真实网络与原规格有三处差异，下表以实测为准：

| 指标 | 原纸面值 | **实测值** | 说明 |
|---|---|---|---|
| 参数量 | 0.584 M | **0.5297 M** | 解码器 skip 通道对齐方式不同 |
| INT8 权重 | 571 KB | **517.3 KB** | |
| 算力 | 2.217 GMAC·s⁻¹ | **1.226 GMAC·s⁻¹** | 原成本模型把步长层按**输入**分辨率计费，高估约 4 倍 |
| 7020 RTF | 0.101 | **0.056** | 只用掉实时预算的 5.6% |
| 分块 | 12 帧 | **必须为 8 的倍数 → 建议 16 帧** | 12 帧会在最后一级下采样出现半帧，skip 对不上 |
| 通路延迟 | 110 ms | **133.5 ms**（改为 16 帧后） | 仍在按键产品的可接受范围 |
| 片上激活 | 452 KB | **452 KB（流式口径）**；朴素逐层口径 16 帧时 64 KB、1 秒分块时 704 KB | **口径必须写死**，见验证报告 §3 |
| 频带数 | 128 | **建议重新权衡**：128 频带掩码比全分辨率损失 **4.06 dB**；256 频带可收回大半 | 可考虑牺牲通道宽度换频带数 |
| 因果性 | 设计目标 | **已验证通过** | 扰动末帧仅影响末帧输出 |

**结论：架构可行，且比原规格更宽裕。但 128 频带这个选择有 4.06 dB 的真实代价，原规格没有量化过它。**

## 10. 下一步与待确认

**待你确认的一点**：能否把延迟预算从 100ms 放宽到 ~150ms？
- 同意 → 采用 **chunk=16**（必须为 8 的倍数，16 帧 / 133.5ms），DDR 带宽余量提升 3 倍（推荐）
- 不同意 → 退回 **chunk=8** / 约 87ms，模型与算力完全不变，仅 DDR 预算收紧

**第一个该做的事：训练。** 目标模型目前**只有架构、没有权重**，因此拿不出任何"它自己分离出来的"音频。所有可听的素材要么来自参考模型，要么是管线验证。唯一路径是用 HTDemucs 在用户 DJ 库上打伪标签做蒸馏训练（模型只有 0.53M 参数，CPU 可训，完全绕开 22.7GB 下载）。建议先跑 20–30 首 × 30s 的冒烟验证。

**第二个该测的数**（比测质量更重要）：
> **同一网络结构下，"严格因果" vs "200ms 前视" vs "非因果" 的 SDR 差多少。**

这是整个方案里唯一还没有答案的关键数。文献经验值是 0.5–1.5 dB，但不能照搬 —— 上一轮已经发现，HTDemucs 去掉 Transformer 后质量几乎没掉，说明这类模型的"上下文收益"可能被高估。
