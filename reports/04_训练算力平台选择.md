# 训练算力平台选择：CPU vs GPU（实测）

> 结论先行：**用 GPU**。但理由不是"CPU 跑不动"——CPU 完全跑得动，
> 真正的理由是**迭代速度**，详见 §4。
>
> 全部数字来自本机实测（`scripts/10_cpu_vs_gpu.py`），不是估算。

---

## 0. 环境变更记录

本轮做了一件改变后续所有工作方式的事：**把 CPU 版 PyTorch 换成了 CUDA 版**。

| 项 | 变更前 | 变更后 |
|---|---|---|
| torch | 2.14.0+**cpu** | 2.14.0+**cu126** |
| torchaudio | 2.11.0+**cpu** | 2.11.0+**cu126** |
| `torch.cuda.is_available()` | `False` | **`True`** |
| 下载量 | — | torch wheel **2.42 GiB** + torchaudio 2.0 MB |
| 耗时 | — | 下载约 10 min（3–4 MB/s）+ 解包约 20 min |

**版本号没有降级**（还是 2.14.0），所以不存在 API 兼容性风险。

### 一个必须先澄清的误判

之前 `nvidia-smi` 一直报 `Failed to initialize NVML: Unknown Error`，
一度让人以为显卡不可用。**这是误报**——直接用 `ctypes` 调 CUDA 驱动 API 的结果：

```
nvcuda.dll loaded OK
cuInit(0)          -> rc=0  (CUDA_SUCCESS)
driver CUDA version: 13.4
cuDeviceGetCount   -> rc=0  count=1
  device 0: NVIDIA GeForce RTX 4070 Laptop GPU
```

显卡从始至终都是好的，只是 `nvidia-smi` 自身的 NVML 初始化路径有问题。
**教训：不要用 `nvidia-smi` 的成败判断 CUDA 可用性**，要直接问驱动。

### 实机规格

| 项 | 值 |
|---|---|
| GPU | NVIDIA GeForce RTX 4070 Laptop GPU |
| 计算能力 | `sm_89`（Ada Lovelace，支持 bf16 / TF32 / tensor core） |
| 显存 | **8.00 GB**（空闲时余 4.33 GB） |

### 回归验证（换后端是否破坏已有结果）

用同一段音频重跑 Open-Unmix 分离，与替换前的输出逐样本比对：

| 指标 | 值 |
|---|---|
| 比对样本数 | 1,764,000 |
| 最大绝对误差 | **0.000e+00** |
| 是否逐位一致 | **是** |
| 全部评测依赖导入 | 10/10 通过（torchaudio / demucs / openunmix / museval / librosa / …） |

**结论：替换后端零回归，之前所有评测结论仍然有效。**

## 1. 实测对比

CPU 用 **20 线程**（不是 28——见 §3），GPU 用 RTX 4070。批次 16，每样本 128 帧
（128 ÷ 172.27 帧/秒 = 0.743 秒音频）。

### 阶段 A：教师伪标签生成（HTDemucs 前向，7.8 s 段）

| 设备 | 每段耗时 | RTF | 吞吐 |
|---|---|---|---|
| CPU（20 线程） | 2654 ms | 0.340 | **2.94** 音频秒 / 墙钟秒 |
| GPU | 145 ms | 0.0185 | **53.94** 音频秒 / 墙钟秒 |
| | | | **加速 18.3×** |

### 阶段 B：目标模型（0.53 M 参数因果 U-Net）训练步

| 设备 | 精度 | 每步耗时 | 吞吐 |
|---|---|---|---|
| CPU | fp32 | 411.1 ms | **28.9** 音频秒 / 墙钟秒 |
| GPU | fp32 | 31.1 ms | **382.2** 音频秒 / 墙钟秒（13.2×） |
| GPU | **bf16 混合精度** | 27.4 ms | **433.8** 音频秒 / 墙钟秒（15.0×） |

### 附：目标模型纯前向（= 产品推理速度，与 FPGA 无关，仅供参照）

| 设备 | 每批耗时 | 吞吐 |
|---|---|---|
| CPU | 164.5 ms | 72.3 音频秒 / 墙钟秒 |
| GPU | 14.2 ms | **839.7** 音频秒 / 墙钟秒 |

### 附：STFT 前处理

| 设备 | 每 10 s 音频 | 吞吐 |
|---|---|---|
| CPU | 1.27 ms | 7877 音频秒 / 墙钟秒 |
| GPU | 0.39 ms | 25458 音频秒 / 墙钟秒 |

**STFT 比训练步快 250 倍以上 → 数据管道不是瓶颈**，不需要为了喂 GPU
而去折腾异步 DataLoader 或 GPU 侧 STFT。这是反直觉但很有用的结论。

### GPU 显存占用

| 场景 | 峰值显存 |
|---|---|
| HTDemucs 教师前向 | **2022 MB** |
| 目标模型训练（batch 16） | **526 MB** |
| 目标模型训练（batch 128） | 4179 MB |

都在 8 GB 之内，**也都在空闲时那 4.33 GB 之内**。

## 2. 批量大小扫描：GPU 根本没被喂饱

| batch | ms/step | 音频秒/墙钟秒 | 显存 |
|---|---|---|---|
| 8 | 13.4 | 445 | 298 MB |
| 16 | 32.4 | 367 | 526 MB |
| 32 | 57.2 | 416 | 1051 MB |
| 64 | 107.9 | 441 | 2093 MB |
| 128 | 213.1 | 446 | 4179 MB |

**吞吐从 batch 8 到 128 几乎不变（~440–450）**，只有显存线性增长。

这说明：模型太小（0.53 M 参数 / 1.23 GMAC/音频秒），GPU 的瓶颈不是算力，
而是**小张量下的 kernel 启动开销**。实际算力利用率只有约 16%。

**结论：批量取 8–32 即可**（显存 300 MB–1 GB，吞吐已到平台期）。
不要为了"跑满 GPU"去加大批量，那只会白吃显存。

---

## 3. CPU 线程数：多开线程反而更慢

同一段 7.8 s 音频，HTDemucs 前向：

| 线程数 | RTF | 吞吐 |
|---|---|---|
| 7 | 0.882 | 1.13 音频秒/墙钟秒 |
| 14 | 0.308 | 3.25 |
| **20** | **0.306** | **3.27** ← 最优 |
| 28（全部逻辑核） | 0.333 | 3.01 |

i7-14700HX 是 8 个性能核 + 12 个能效核、共 28 逻辑线程。**开满 28 线程会因
超线程争抢而变慢**，7 线程则严重欠占用（慢 2.9 倍）。

**项目约定：CPU 侧固定 `torch.set_num_threads(20)`。**
（原 `common.py` 里是 `cpu_count()//2 = 14`，建议同步改成 20。）

### 另一个坑：装完立刻跑基准会慢 2.4 倍

第一次跑基准时 CPU 教师是 RTF 0.81，隔一会儿重跑变成 0.340。
原因是刚解包完 14,000 个文件（4.0 GB），Windows Defender 还在后台扫描新 DLL。
**教训：装完大包后要等系统安静下来再测性能，否则会得出错误结论。**

## 4. 落到实际训练计划

按 **20 线程 CPU** 与 **GPU bf16** 对比：

| 素材时长 | 生成伪标签 CPU | 生成伪标签 GPU | 训练 1 epoch CPU | 训练 1 epoch GPU |
|---|---|---|---|---|
| 1 h | 0.34 h | **1.2 min** | 0.03 h | **4 s** |
| 3 h | 1.02 h | **3.4 min** | 0.10 h | **11 s** |
| 10 h | 3.40 h | **11 min** | 0.35 h | **36 s** |
| 30 h | 10.20 h | **34 min** | 1.04 h | **1.8 min** |
| 100 h | 34.01 h | **1.85 h** | 3.46 h | **14 min** |

### 一个现实的方案：3 小时素材（约 40 首）

| 步骤 | CPU | GPU |
|---|---|---|
| 生成伪标签 | 1.02 h | **3.4 min** |
| 训练 100 epoch | 10 h | **1 h** |
| **合计** | **≈ 11 h** | **≈ 1.1 h** |

### 冒烟验证：30 首 × 30 s（15 分钟音频）

| 步骤 | CPU | GPU |
|---|---|---|
| 生成伪标签 | 5.1 min | **17 s** |
| 训练 30 epoch | 15.6 min | **1 min** |
| **合计** | **≈ 21 min** | **≈ 1.3 min** |

### 真正决定性的理由

单看一次训练，CPU 的 11 小时也算"挂一晚上就完了"。**但训练不是一次性的**——
整个方案里唯一还没有答案的关键数是：

> **同一网络结构下，「严格因果 / 200 ms 前视 / 非因果」的 SDR 差多少。**

要回答它得跑消融实验。假设一轮消融 20 次配置：

| | CPU | GPU |
|---|---|---|
| 20 次实验 × 每次 (标签 + 100 epoch) | **≈ 220 h（9 天）** | **≈ 22 h（1 天）** |

**这才是 GPU 的价值：不是"能不能跑"，而是"一天能试几版"。**
在这个需要反复试错的阶段，15× 的差距会把一周变成一天。

## 5. 推荐的运行配置

```python
import torch
torch.set_num_threads(20)                      # 实测最优；勿用 28
torch.backends.cudnn.benchmark = True          # 输入尺寸固定，开自动调优
device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
batch_size = 16                                # 8–32 均可，吞吐已平台化
autocast = torch.bfloat16                      # sm_89 原生支持，+15% 吞吐
```

| 决策 | 取值 | 依据 |
|---|---|---|
| 训练设备 | **GPU** | 15.0× 于 CPU |
| 教师推理设备 | **GPU** | 18.3× 于 CPU，且这是真正的瓶颈 |
| 精度 | **bf16 混合精度** | 比 fp32 快 15%，Ada 原生支持 |
| 批量 | **8–32** | 吞吐已平台化，显存 0.3–1 GB |
| CPU 线程 | **20** | 28 线程反而慢 8% |
| 数据管道 | 保持 CPU 同步加载即可 | STFT 比训练步快 250×，不是瓶颈 |
| 兜底 | CPU 路径仍然可用 | 只是慢 15×，用于验证与调试 |

## 6. 限制与待办

- [ ] **`common.py` 的线程数仍是 `cpu_count()//2 = 14`**，实测最优是 20，
      建议改成 `min(20, cpu_count())`。
- [ ] 本报告的吞吐是**合成随机张量**测的。真实训练的瓶颈会变成
      **磁盘 I/O + 音频解码**，需要用真实 DJ 素材再测一次端到端。
- [ ] 显存空闲时只有 4.33 GB（有约 3.67 GB 被桌面/虚拟显示占用）。
      训练本身只要 0.5 GB，但若要同时跑教师推理与训练需留意。
- [ ] 若这台机器通过 GameViewer 等远程工具共享显卡，多人并发时显存会紧张。
